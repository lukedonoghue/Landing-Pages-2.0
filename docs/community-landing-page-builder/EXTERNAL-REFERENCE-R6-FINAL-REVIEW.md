## Cleared false positives

**The popup does not leak keyboard focus to background page controls in the tested Chrome cases.** Parent traced 27 forward and 27 reverse Tab steps at each of six sizes: 324 steps total. The body-only transitions have `document.hasFocus() === false`, no active page control, and the next step returns inside the dialog. An attempt to focus the outside header phone remains blocked. This is consistent with native browser-chrome focus, not a reachable background control. Preserve the original raw failures, but do not treat them as six page defects. See `parent/final/focus-calibration.json` and the script.

The distinction is supported by [Document.hasFocus documentation](https://developer.mozilla.org/en-US/docs/Web/API/Document/hasFocus): an active element need not currently have focus. [Native dialog documentation](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog) describes modal background inertness. Browser-chrome identification is an inference from the recorded transition, document-focus flag, return path and blocked outside focus. This is not a cross-browser or physical-device certification.
