# Branded Lead Funnel Builder

Build one coherent funnel, not four disconnected artifacts:

1. a responsive static landing page;
2. one CTA-triggered multi-step lightbox form;
3. a brand-matched services catalogue or brochure PDF;
4. a thank-you page that delivers the brochure and states the exact follow-up;
5. an authenticated CRM with a pipeline, lead table, notes, attribution, and daily visitor/conversion reporting;
6. one guided Cloudflare publishing flow and a verified client handoff.

Cloudflare is the only required hosting platform: Workers serves the public page, brochure, admin CRM and API; D1 stores leads, notes, sessions and visitor/conversion records. Use one D1 database per client/site. GitHub is optional source backup/version control, never a prerequisite. Supabase, Netlify and external analytics accounts are not required. Omit the CRM only when requested. Keep public marketing files independent of the admin bundle. A handoff-only or catalogue-only task does not add infrastructure to an existing site.

Replicate the reference page's **persuasive jobs, section order, pacing, and CTA logic**. Never copy its wording, claims, brand, proprietary assets, or pixel design.

## Publishing intent

Improving this reusable skill or testing its sample project is not a request to publish the current client page. Keep those tasks local. When a future user asks to publish their generated funnel, guide one **Publish to Cloudflare** action: reuse or connect their Cloudflare account, choose their domain or a workers.dev address, provision/bind D1, configure admin access, run final checks, deploy and verify. The agent handles the internal commands; do not send the user between hosting/database/analytics products or insist on a GitHub repository. First-time sign-in and domain ownership may need the user, so describe the experience as one guided publishing flow rather than promising zero setup.

## Required user journey

Accept a client website as the minimum input. Reference page, audience/service brief and offer idea are optional. Research first, propose a concise brief and use curated examples when no reference is supplied. Ask only about consequential unknowns; never invent a price, guarantee, included service or follow-up deadline.

Run this sequence:

**Research → copy draft and editorial review → user copy approval → design and imagery → browser/visual/performance/form testing → fixes and rechecks → user final publishing approval → Cloudflare deployment and live verification.**

The two planned approval checkpoints are mandatory for a complete funnel. A writer/reviewer pass is not user approval. Everything between them can proceed autonomously within the user's scope. Preserve an approval while the exact approved copy/offer stays unchanged; a material revision requires a new approval. Use `scripts/workflow.py` and [references/approval-workflow.md](references/approval-workflow.md) to retain the actual approval message and revision. Never record an invented user approval.

## Select the mode

- **Copy-only or copy review:** use [references/copy-only-test.md](references/copy-only-test.md); do not scaffold CRM, HTML or publishing infrastructure.
- **Complete funnel:** research, strategy, copy, catalogue, build, QA, and handoff.
- **Refresh existing funnel:** preserve working behavior; re-audit claims, brand, copy, assets, form, catalogue, and QA before editing.
- **Catalogue-only or page-only:** run the shared research and claim gates, then only the relevant production workflow.
- **Handoff-only:** inspect and verify existing artifacts; do not describe local checks as deployment proof.

## Research and evidence gate

Read [references/research-and-claims.md](references/research-and-claims.md).

- Inspect the client site, relevant service/process/FAQ/testimonial pages, the reference page, and supplied files.
- Capture the reference and client pages at desktop and mobile sizes.
- Record what each reference section accomplishes: promise, proof, mechanism, objection handling, process, offer, CTA.
- Extract client brand tokens, services, outcomes, differentiators, imagery, contact details, reviews, and form requirements.
- Put every factual or numeric claim in `docs/CLAIM-LEDGER.md` with source, confidence, approval, qualifiers, and date if time-sensitive.
- Never invent reviews, profile photos, customer counts, prices, guarantees, response times, licenses, insurance, certifications, before/after pairs, or results.

For public Google reviews, verify the listing using the client's exact phone and website. Keep name, rating, quote, and profile image tied to the same public review. Use an initials avatar when Google does not expose a real photograph. Recheck rating/review counts immediately before launch.

## Strategy and copy gate

Read [references/copy-doctrine.md](references/copy-doctrine.md), [references/copy-workflow.md](references/copy-workflow.md) and [references/copy-and-structure.md](references/copy-and-structure.md). The bundled curated reference library is part of this skill, not a separately configured database. Use `scripts/copy_project.py` for source capture and `scripts/copy_library.py` to select relevant curated examples, prepare context, render the master and audit the actual editorial review. Exclude quarantined OCR and unreviewed examples from writing instructions.

For new builds keep `build/page-copy.json` as the canonical master and derive `docs/SECTION-COPY.md`. Before design, show the complete customer-facing draft to the user and record their approval with `workflow.py approve-copy`. Run `workflow.py check-copy` before visual assembly. Readiness helpers must not replace the writer or the editorial reviewer.

Before HTML, produce:

- `docs/REFERENCE-PAGE-COMPARISON.md`
- `docs/BUYER-PSYCHOLOGY.md`
- `docs/OBJECTION-MAP.md`
- `docs/DESIGN-SYSTEM.md`
- `docs/SECTION-COPY.md`
- `docs/COPY-GATE-CHECKLIST.md`

The copy gate passes only when:

- the hero matches search/source intent and names the desired after-state;
- section headlines are skimmable benefit claims;
- proof appears early and again near relevant claims;
- one exact CTA phrase names the deliverable;
- page, modal, thank-you page, and brochure use the same offer and follow-up promise;
- objections are handled with sourced evidence;
- testimonials are faithfully shortened without changing meaning;
- no unsourced claim survives.

## Design and image workflow

After copy approval, create a cohesive design direction from the client brand and the reference's persuasive structure. Run [references/image-workflow.md](references/image-workflow.md): plan placements, inventory observed client assets, source suitable real imagery, identify opportunities for illustrative generation, register actual outputs, optimize and inspect desktop/mobile crops.

Use native image generation when available; requested GPT Image 2.5 identity must be reported by the actual tool/provider before claiming it. Keep a bounded generation budget, provenance and exceptions. Never silently substitute models or fabricate client work/staff/testimonials. Model/tool access is a setup dependency, not a reason to fake success. Generated images are saved as ordinary local assets and are hosted on Cloudflare after publishing; no image API key belongs in the deployed page.

Use `scripts/image_workflow.py --plan <project>/image-plan.json validate` and `workflow.py record-image-evidence` for actual image QA. A page needing no raster imagery may document a specific reason; do not create meaningless decorative assets to satisfy a checklist.

## Catalogue workflow

Read [references/catalogue-workflow.md](references/catalogue-workflow.md) and the PDF skill before creating or editing a PDF.

- Reuse the same claim ledger, brand tokens, outcome language, offer, phone, and URLs as the page.
- Organize the catalogue around buyer decisions and service fit, not a generic company profile.
- Include a cover, service-selection overview, service pages, process, proof, and a final CTA/contact page.
- Use `assets/catalogue.example.json` with `scripts/build_catalogue.py` as a starting point when suitable.
- Render every page, inspect a contact sheet, verify page count and links, then generate lightweight WebP cover images with `scripts/render_catalogue_cover.py`.
- The landing page loads the cover image only; the full PDF is delivered after conversion unless the user requests otherwise.

## Build contract

Read [references/build-contract.md](references/build-contract.md).

Default to semantic static HTML/CSS/JavaScript when no framework is required. Build from the client's real brand and the reference's conversion logic.

Default funnel behavior:

- the hero keeps the core visual subject visible;
- the header exposes a prominent click-to-call phone number when phone calls matter;
- the compact brochure/estimate CTA uses one exact phrase everywhere;
- every CTA opens the same accessible multi-step lightbox;
- no duplicate inline form unless explicitly requested;
- no extra form fields, uploads, or open-ended questions unless requested or approved;
- the thank-you page confirms the promised next step and provides the brochure download;
- images have responsive variants, explicit dimensions, and below-fold lazy loading;
- fonts are local where practical;
- UTM and click IDs persist through submission;
- analytics never receives raw contact details; built-in reporting uses only pseudonymous visitor and receipt identifiers.

The built-in reporting needs no contact data in analytics at all: send only a pseudonymous visitor ID and a committed receipt ID. Optional advertising enhanced conversions require a separate verified provider adapter and applicable consent.

Use `assets/multistep-lightbox.js` for the fragile modal, validation, focus, attribution, tracking-hook, webhook, and redirect mechanics when its DOM contract fits.

Use the same-origin `/api/leads` endpoint with [references/lead-and-tracking-contract.md](references/lead-and-tracking-contract.md). An HTTP 200 is not sufficient: require `ok: true` and a receipt from the stored CRM record. Keep idempotency across uncertain retries. A failed analytics/webhook integration must never turn a stored lead into an apparent form failure.

## Admin and operations

The Cloudflare module includes named owner login, hashed passwords and server-side sessions. Configure `ADMIN_USERNAME` during setup; never ship a generic fallback or credentials in client JavaScript. Account controls provide password rotation, session revocation, new-lead notifications and CSV export. [references/admin-access-and-recovery.md](references/admin-access-and-recovery.md) covers secure owner recovery and tested D1 backup/restore. Built-in notifications stay in the CRM; email/webhook destinations are optional.

## QA and handoff

Read [references/qa-and-handoff.md](references/qa-and-handoff.md).

Use [references/measured-qa.md](references/measured-qa.md) for the executable browser and evidence workflow. Test 360, 390, 768, 1024, 1180, 1280, and 1440 widths plus short laptop heights. Test the public flow and CRM independently.

Run:

```bash
python3 scripts/validate_funnel.py <project-root> \
  --cta "<exact CTA>" \
  --brochure "assets/brochure/<file>.pdf"
```

Also run the measured stages in [references/performance-and-browser-qa.md](references/performance-and-browser-qa.md): mobile Lighthouse budgets, Chromium and WebKit, and the real local form-to-D1-to-CRM journey. Missing tools or browsers are blockers, not silent skips. Performance reports keep raw measurements; TBT is a lab proxy, not field INP. Inspect screenshots with ChatGPT and repair visible issues even if numeric checks pass.

Then verify in a real browser:

- hero composition and contrast;
- every CTA opens the same modal;
- Escape, backdrop close, focus trap, and focus restoration;
- required validation and Back/Continue behavior on every step;
- exact form field scope;
- webhook success and failure behavior;
- thank-you redirect and brochure download;
- phone and privacy links;
- console/network errors;
- desktop/mobile layouts and lazy-loaded imagery.

ChatGPT/Codex must actually view the captured desktop, mobile, modal, thank-you, CRM, and catalogue images. Use an isolated browser or computer-use session where useful. A measurement report is not a visual review. Record exact screenshots, findings, fixes, remaining limits, and the source fingerprint in a visual report. Re-render affected screens after fixes. Use [references/feedback-and-review.md](references/feedback-and-review.md) for corrections and independent review.

For the backend, run `npm test` in the generated project. Then test the real local Worker/D1 route: visitor → form → receipt → stored contact → CRM stage change/note → reporting. Confirm unauthorized admin/API requests fail. Do not substitute a mocked UI or direct thank-you navigation for this test. The harness blocks write requests by default; separate controlled functional tests must explicitly use an isolated local database or an authorized live test lead.

Use only these gate states: `pass`, `pass_with_warnings`, `blocked`, or `not_applicable`. Never record `pass` while named required evidence is missing.

Before the final publish approval, present the finished page, brochure, form, thank-you page and admin experience with concise test results and any remaining limitations. Explicitly include whether a controlled live test lead is authorized in that approval. `workflow.py check-publish` must pass before `npm run publish`; both user approvals and the current copy, image, performance, browser and visual evidence are required.

The publish command executes post-deployment verification against the actual destination. It must distinguish uploaded, read-only checks passed, and the fully verified lead/CRM/tracking journey. A full pass needs actual receipt correlation, not a console message asking someone else to test it.

Use `scripts/package_handoff.py` only after local QA. The handoff must say whether lead delivery, analytics, advertising conversions, final-domain links, and deployment were actually tested.

For Workers projects, use the Workers-aware handoff packager and publishing guide; a static ZIP alone cannot run D1 or the CRM. Evidence gates bind checks and screenshots to the current source; source changes invalidate earlier results. Preview, handoff, and live verification are distinct statuses.
